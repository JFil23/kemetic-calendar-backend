A deployment requires the complete exact-source backend and admin gates. Preserve
the default opaque keys, cron secrets, schedules, callback identity, RLS and app
assets. Verify legitimate and forged-session boundaries before changing signing.
Import the legacy signing key, rotate to a new asymmetric key and preserve valid
old sessions for the configured lifetime plus the documented 15-minute margin
(75 minutes at the current one-hour lifetime). Only then disable legacy API keys
and revoke old signing trust. Verify denial of the exposed token as both API key
and bearer while new sessions, refreshes, service calls and app flows work.
Never re-enable the exposed key as routine rollback.

This preparation is not evidence that retirement has happened. Deployment and
per-service verification receipts belong in .git/deployment-receipts. The live
version.json remains the application deployment authority. App source, visual
references and persisted keys are unchanged by this backend migration.

not silently enroll an agent-owned factor. The encrypted recovery archive and

## Completed cutover and compatibility evidence

The owner explicitly approved the final authentication migration. Legacy API keys
were disabled and the HS256 signing key was revoked on November 11. The ES256
signer is in use. All three isolated test accounts refreshed to ES256 and retained
their private-flow and sender/recipient share access; the unrelated account could
not read the private flow or share. The 17 original gateway checks were briefly
migrated to the independently verified handlers, then restored after live probes
confirmed the current gateway supports ES256 and the public guest key. The builder
now preserves every baseline gateway flag. Handler checks remain mandatory.

A fresh pre-revocation audit found zero non-test sessions issued or refreshed in
the previous 75 minutes; the latest real session activity was November 10 at
14:40 UTC. Thus no legitimate old access token remained valid at rotation. The
three controlled sessions were refreshed before revocation. This quiescent
cutover preserves the grace period's purpose without an idle monitoring loop.

including REST, Storage, Auth administration and Realtime. During propagation a
bare apikey-only REST request briefly received anonymous public access, returning
no private fixture rows. The final 23:34 UTC check returned 401 for that form too,
while the current user still read its own fixture and the publishable key saw no
private rows. Receipts retain the initial strict probe failure, the ownership
diagnosis, and the final complete rejection after propagation.

The public production, RC and admin clients use publishable keys. Dormant native
builds using the legacy anon JWT must update; legacy keys must not be re-enabled.
